## 1. Что такое PEFT

PEFT — Parameter-Efficient Fine-Tuning, то есть дообучение небольшой части параметров большой модели. Базовые веса Llama-7B заморожены, поэтому:

- требуется намного меньше памяти для градиентов и состояния оптимизатора;
- обучение помещается на T4;
- исходные знания модели в основном сохраняются;
- сохранять можно только небольшие обученные добавки.

В ноутбуке рассмотрены два варианта PEFT:

- prompt tuning — обучение виртуальных токенов перед настоящим текстом;
- LoRA — обучение низкоранговой поправки к линейным слоям.

Сама Llama загружается в 4-битном виде. Квантованы большие замороженные матрицы, а небольшие обучаемые параметры остаются в более точном формате.

## 2. Собственный prompt tuning

### Идея

Пусть обычная последовательность содержит `S` токенов, а размер скрытого представления равен `H`. Обычный слой эмбеддингов возвращает тензор формы:

```text
[batch_size, S, H]
```

Мы добавляем `P = 16` обучаемых векторов формы:

```text
[1, P, H]
```

В каждой строке батча первые 16 технических PAD-токенов заменяются этими векторами. Благодаря `expand` промпт логически повторяется для всего батча без физического копирования данных.

Ключевая последовательность действий в `WordEmbeddingsWithLearnedPrompts.forward`:

1. Получить обычные эмбеддинги для `input_ids`.
2. Расширить `learnable_prompts` до размера батча.
3. Отбросить обычные эмбеддинги первых 16 PAD-позиций.
4. Склеить обучаемый промпт с оставшимися эмбеддингами по измерению последовательности `dim=1`.

### Почему PAD-токены добавляются вручную

Собственная реализация не умеет сама увеличивать входную последовательность. Поэтому перед настоящими токенами резервируются позиции. Их значения не важны: обычные эмбеддинги этих позиций заменяются обучаемыми.

В `attention_mask` для них стоят единицы. Это важно: модель должна видеть виртуальные токены и использовать их в механизме внимания.

### Почему логиты и targets сдвинуты

Языковая модель предсказывает следующий токен:

```text
логит в позиции t → настоящий токен в позиции t + 1
```

Первые `num_prompts` логитов относятся к виртуальному промпту и не сравниваются с текстовыми целями. Поэтому используются:

```python
next_word_logits = outputs.logits[:, num_prompts:-1, :]
true_next_tokens = input_ids[:, num_prompts + 1:]
```

Обе части после этого имеют одинаковое число позиций.

### Цикл обучения

На каждом шаге выполняются стандартные операции:

1. `zero_grad(set_to_none=True)` очищает старые градиенты с меньшими накладными расходами.
2. Прямой проход вычисляет логиты.
3. `cross_entropy` измеряет ошибку следующего токена.
4. `loss.backward()` вычисляет градиент только для обучаемого промпта.
5. `opt.step()` обновляет промпт.
6. Обучение останавливается при `loss <= 0.1`.

Такое обучение фактически запоминает одну целевую фразу. Это учебная демонстрация, а не универсальное дообучение модели.

## 3. Prompt tuning через Hugging Face PEFT

Перед разделом загружается чистая модель. Затем вызывается:

```python
peft.prepare_model_for_kbit_training(...)
```

Эта стандартная функция подготавливает квантованную модель к обучению: замораживает базовые параметры, настраивает нужные типы данных и работу gradient checkpointing.

`PromptTuningConfig` задаёт 16 виртуальных токенов. В отличие от ручной реализации, PEFT добавляет их внутри модели, поэтому PAD-токены к `input_ids` больше не добавляются.

Learning rate равен `1e-2`. Для нескольких обучаемых prompt-векторов это нормальная величина: она намного больше типичных `1e-5` для полного fine-tuning. Используется `AdamW` только с параметрами, у которых `requires_grad=True`.

Логиты PEFT всё равно включают виртуальные позиции, поэтому первые 16 логитов пропускаются. Целевые `input_ids` при этом виртуальных токенов не содержат.

## 4. Собственный LoRA

### Формула

Исходный линейный слой вычисляет:

```text
Y_base = XW + b
```

LoRA добавляет обучаемую низкоранговую поправку:

```text
Y = Y_base + XAB
```

Если `W` имеет размер `in_features × out_features`, то:

- `A`: `in_features × rank`;
- `B`: `rank × out_features`;
- `rank = 8`, то есть намного меньше исходных размеров слоя.

В коде вычисление записано как:

```python
lora_output = (input @ adapter_A) @ adapter_B
```

Скобки важны: сначала представление уменьшается до размерности `rank`, а затем разворачивается к `out_features`. Это и даёт экономию.

### Почему B начинается с нулей

`adapter_A` инициализируется случайно, а `adapter_B` — нулями. Поэтому в начале:

```text
XAB = 0
```

и новый слой полностью повторяет исходный. После первого шага градиент изменяет `B`, затем обучение начинает эффективно менять обе матрицы.

### Какие слои адаптируются

Основной код добавляет LoRA к `q_proj`, `k_proj` и `v_proj` каждого из 32 attention-блоков Llama. Получается 96 адаптеров.

Для итогового задания дополнительно адаптируется `lm_head`. Это выходной слой, который преобразует скрытое представление в логиты словаря. Такой выбор:

- выполняет условие задания о дополнительном адаптере;
- требует меньше памяти, чем LoRA сразу во всех MLP-слоях;
- напрямую помогает изменить распределение следующего токена в сторону Python-кода;
- удобен для T4 с 16 ГБ памяти.

В класс намеренно не добавлен множитель `alpha / rank`: предоставленные тесты ожидают ровно формулу `XAB`.

## 5. Данные CodeParrot

`codeparrot/codeparrot-clean` содержит очищенные Python-файлы, а исходный код лежит в поле `content`.

Весь датасет большой, поэтому используется `streaming=True`. Это означает, что примеры читаются по мере необходимости и не загружаются целиком на диск.

Порядок подготовки:

1. Поток перемешивается с фиксированным `seed=42`.
2. Берутся 2500 примеров.
3. Пустые примеры отбрасываются.
4. Из `content` берутся первые 512 символов: `content[:512]`.
5. Только после символьного среза текст токенизируется.
6. `DataCollatorForLanguageModeling` динамически дополняет примеры до длины максимального примера текущего батча.

Важно различать символы и токены. Условие требует именно 512 символов. Если сначала токенизировать и взять 512 токенов, получится существенно более длинный текст и условие будет нарушено.

Параметр `max_length=512` при токенизации является дополнительной страховкой для необычных последовательностей. Обычный фрагмент из 512 символов Python занимает заметно меньше 512 токенов.

## 6. Генерации до и после обучения

Функция `generate_samples`:

- переключает модель в `eval()`;
- использует левый padding, корректный для батчевой генерации decoder-only модели;
- генерирует батчами по четыре промпта, чтобы не переполнять память T4;
- использует `torch.inference_mode()`;
- включает FP16 autocast;
- делает детерминированный greedy decoding с `do_sample=False`;
- генерирует до 64 новых токенов.

Генерации до обучения сохраняются до вызова `trainer.train()`. После обучения те же промпты запускаются с теми же настройками. Поэтому изменение результата связано с fine-tuning, а не со случайным sampling.

Для более творческих, но менее воспроизводимых результатов можно позже попробовать:

```python
do_sample=True
temperature=0.8
top_p=0.95
```

Для отчёта детерминированный вариант лучше.

## 7. Настройки итогового обучения

Использованы следующие параметры:

| Параметр | Значение | Причина |
|---|---:|---|
| `per_device_train_batch_size` | 1 | Безопасно для T4 |
| `gradient_accumulation_steps` | 4 | Эффективный batch size равен 4 |
| `max_steps` | 500 | Требование/ориентир задания |
| `learning_rate` | `2e-4` | Распространённое значение для LoRA |
| `warmup_steps` | 50 | Плавный разогрев первые 10% шагов |
| `fp16` | `True` | Ускорение и экономия памяти на T4 |
| `save_strategy` | `no` | Не расходует диск на промежуточные checkpoint |
| `logging_steps` | 10 | Видна динамика loss без слишком частого вывода |

Эффективный размер батча:

```text
1 пример на GPU × 4 шага накопления × 1 GPU = 4
```

`use_cache=False` установлен на время обучения, потому что KV-cache несовместим с gradient checkpointing и при обучении не нужен. Перед генерацией кэш включается обратно.

## 8. Что должно получиться

### Короткий prompt tuning

- Loss должен стать меньше `0.1`.
- Продолжение `A quick brown fox` должно приблизиться к целевой фразе с `did not jump...`.

### LoRA

- Все unit-тесты `LoRALayer` должны пройти.
- Проверка должна обнаружить ненулевые градиенты у `adapter_B`.

### Итоговое обучение

- Training loss должен в среднем снижаться, хотя отдельные значения могут колебаться.
- После обучения генерации чаще должны содержать Python-синтаксис: импорты, определения функций, условия, циклы и вызовы библиотек.
- За 500 шагов модель не обязана стать полноценной code-моделью. Задание просит показать направление изменения, а не добиться полной сходимости.

## 9. Почему loss может колебаться

На каждом шаге поступают разные фрагменты кода. Один пример может быть простым, другой — содержать редкие имена и длинные строки. Поэтому локальный loss не обязан монотонно уменьшаться. Оценивать нужно общий тренд, а также сравнение генераций.

## 10. Частые проблемы

### `CUDA out of memory`

1. Перезапустить среду Colab.
2. Убедиться, что выбран T4 GPU.
3. Выполнять ячейки строго один раз сверху вниз.
4. Оставить `per_device_train_batch_size=1`.
5. Уменьшить `max_new_tokens` при генерации с 64 до 32.
6. Уменьшить `batch_size` в `generate_samples` с 4 до 2 или 1.

Не нужно уменьшать `gradient_accumulation_steps=4`, потому что это нарушит требование об эффективном batch size не меньше четырёх.

### Предупреждение о `use_cache`

Если появляется сообщение о несовместимости cache и gradient checkpointing, проверить, что перед `trainer.train()` выполнено:

```python
model.config.use_cache = False
```

### Dataset долго начинает загружаться

При `streaming=True` скачивается только поток необходимых шардов. Первый доступ всё равно зависит от скорости Hugging Face Hub. Не следует заменять потоковую загрузку обычной загрузкой полного датасета.

### Loss prompt tuning не достиг 0.1

Сначала повторить запуск с теми же параметрами. Из-за случайной инициализации иногда требуется больше шагов. Затем можно увеличить `max_steps` со 100 до 150. Learning rate лучше оставить `1e-2`.

### Модель генерирует бессмысленный код

Это не обязательно ошибка: 500 шагов очень мало для Llama-7B общего назначения. В отчёте можно честно показать, какие признаки Python появились и какие проблемы сохранились.

### Ошибка после повторного запуска ячейки добавления LoRA

Не следует оборачивать один и тот же слой в `LoRALayer` второй раз. Самый надёжный способ — перезапустить runtime и выполнить ноутбук заново сверху вниз.

## 11. Как читать итоговую таблицу

Сравнивать стоит не только внешнюю осмысленность текста, но и измеримые признаки:

- появились ли `def`, `class`, `import`;
- стали ли корректнее отступы;
- появились ли парные скобки и двоеточия;
- продолжает ли модель ключевые слова `while`, `if`, `for`, `try` подходящей конструкцией;
- стала ли генерация после `torch` чаще использовать PyTorch API.

В HTML применяется `html.escape`. Без этого символы `<`, `>` и `&` из кода могли бы интерпретироваться браузером как HTML и испортить таблицу.

## 12. Что можно улучшить сверх задания

Если останется GPU-время, можно провести отдельные эксперименты:

- сравнить LoRA для `lm_head` с LoRA для `mlp.up_proj`, `mlp.gate_proj`, `mlp.down_proj`;
- добавить validation split и считать validation loss;
- сохранять только параметры адаптеров;
- увеличить число шагов;
- добавить более содержательные промпты, например сигнатуры функций и docstring;
- проверить синтаксис генераций через `ast.parse`;
- измерить долю генераций, которые являются синтаксически корректным Python.

Эти улучшения не нужны для выполнения текущего обязательного задания.

## Краткая схема всего ноутбука

```text
4-битная Llama-7B
        │
        ├── ручной prompt tuning ── обучаются 16 векторов
        │
        ├── PEFT prompt tuning ──── те же идеи через библиотеку
        │
        └── собственный LoRA
                ├── Q/K/V во всех attention-блоках
                ├── дополнительный lm_head
                ├── генерации до обучения

                └── генерации после обучения + таблица
```

Главная идея задания: большую модель не нужно обучать целиком. Достаточно заморозить её веса и научить сравнительно небольшие параметры управлять входным контекстом или корректировать отдельные линейные преобразования.
